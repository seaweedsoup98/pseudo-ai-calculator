# Mini NPU Simulator 프로젝트 수행 보고서

## 1. 프로젝트 접근

* 이미지 패턴 판별을 숫자 배열과 MAC(Multiply-Accumulate) 연산 문제로 단순화
* 패턴과 필터의 같은 위치 값을 곱한 뒤 모든 결과를 누적하여 점수 계산
* 점수가 큰 필터를 입력 패턴과 더 많이 겹치는 필터로 해석
* 사용자 입력과 JSON 데이터 분석을 별도 실행 모드로 구성
* 연산, 입력, 데이터 검증, 성능 측정을 파일별로 분리하여 역할을 구분

## 2. MAC 연산의 구현

* N×N 패턴과 필터의 모든 위치 `(i, j)`를 순서대로 방문
* 각 위치에서 `pattern[i][j] * filter[i][j]` 계산
* 계산 결과를 하나의 점수에 계속 누적
* N×N 배열에서 방문하는 원소 수는 항상 N²개
* 따라서 단일 MAC 점수 계산의 시간 복잡도는 `O(N²)`

```text
score = 0

각 위치 (i, j)에 대해
    score += pattern[i][j] × filter[i][j]
```

* 이 프로젝트의 패턴 값은 주로 0과 1이고 필터의 관심 위치에는 양의 가중치가 존재
* 입력의 활성 위치와 필터의 관심 위치가 많이 겹칠수록 양의 곱이 많이 누적되어 높은 점수를 얻음
* 따라서 현재 데이터 구조에서는 MAC 점수를 패턴 유사도의 간단한 지표로 사용할 수 있음
* 단, 일반적인 내적이 항상 완전한 유사도 척도인 것은 아니며 입력 크기나 필터 가중치가 크게 달라지는 경우 정규화 등의 추가 정책이 필요할 수 있음

## 3. 데이터 표현과 라벨 정규화

* 외부 JSON 데이터와 프로그램 내부 표현을 직접 결합하지 않도록 라벨 정규화 단계를 분리
* 외부 표현

  * `+`
  * `cross`
  * `x`
* 내부 표준 표현

  * `Cross`
  * `X`
* 입력 형식이 다르더라도 의미가 같다면 하나의 표준 라벨로 변환한 뒤 판정
* 데이터 스키마와 판정 로직 사이의 의존성을 줄일 수 있음
* 향후 외부 데이터의 표기 방식이 변경되더라도 정규화 함수에서 변경을 흡수할 수 있음

## 4. 크기별 필터 선택

* 패턴 키는 `size_{N}_{idx}` 형식을 사용
* 키 자체에서 패턴 크기 N을 추출
* 추출한 N과 동일한 `size_N` 필터를 선택
* 패턴 데이터에 별도의 크기 필드를 추가하지 않아도 키 규칙만으로 필터 연결 가능
* 패턴 또는 필터가 N×N 형태인지 다시 검증하여 키와 실제 데이터가 불일치하는 경우를 구분
* 잘못된 한 케이스 때문에 전체 분석 프로그램이 종료되지 않도록 케이스 단위로 FAIL 처리

## 5. 부동소수점과 비교 정책

* Python `float`는 대부분의 십진 소수를 이진수로 정확하게 표현할 수 없음
* 반복적인 곱셈과 누적 과정에서 매우 작은 표현 오차가 나타날 수 있음
* 실제 실행에서도 다음과 같은 값이 확인됨

```text
0.9
0.8999999999999999

7.499999999999997
7.5

4.9
4.899999999999999
```

* 단순히 `score_a > score_b`만 사용하면 의미 없는 수치 오차가 판정을 결정할 수 있음
* 이를 방지하기 위해 두 점수 차이가 `1e-9`보다 작으면 동점으로 처리
* 사용자 입력 모드에서는 사람이 이해하기 쉬운 `판정 불가`로 출력
* JSON 분석 모드에서는 결과 라벨로 사용하기 쉬운 `UNDECIDED`를 사용
* 두 표현의 의미는 동일하며 각 모드의 출력 목적에 따라 표현만 다르게 구성

## 6. 연산 시간 측정

* 성능 분석의 대상은 파일 읽기나 콘솔 출력이 아니라 MAC 자체
* `time.perf_counter()`를 MAC 함수 호출 직전과 직후에 배치
* 각 크기를 10회 반복 측정한 뒤 평균값 사용
* 입력 생성 및 JSON 로딩은 측정 구간에서 제외
* 짧은 연산은 운영체제 스케줄링, CPU 상태 등의 영향이 크므로 단일 측정값보다 반복 평균이 적절하다고 판단

실제 측정 결과:

| 크기    | 연산 횟수 | 평균 시간(ms) |
| ----- | ----: | --------: |
| 3×3   |     9 |  0.002360 |
| 5×5   |    25 |  0.004700 |
| 13×13 |   169 |  0.023982 |
| 25×25 |   625 |  0.079162 |

* N 증가에 따라 N²이 증가하고 실제 시간도 함께 증가하는 경향 확인
* 작은 입력에서는 함수 호출, 반복문 등의 고정 오버헤드 영향도 있어 정확히 N² 비율로 시간이 증가하지는 않음
* 입력 크기가 충분히 커질수록 원소 방문 횟수의 영향이 상대적으로 커질 것으로 예상

## 7. 2차원 배열과 1차원 배열

* 보너스 구현에서는 N×N 배열을 길이 N²의 1차원 배열로 변환
* 2차원 MAC에서는 행 접근과 열 접근이 반복됨
* 1차원 MAC에서는 하나의 인덱스만 순차적으로 증가
* 동일 데이터와 동일 반복 횟수로 두 방식을 비교

| 크기    |   2D(ms) |   1D(ms) |
| ----- | -------: | -------: |
| 3×3   | 0.002360 | 0.001130 |
| 5×5   | 0.004700 | 0.002372 |
| 13×13 | 0.023982 | 0.012902 |
| 25×25 | 0.079162 | 0.045535 |

* 현재 실행 환경에서는 모든 크기에서 1차원 방식이 더 빠르게 측정됨
* Python에서는 실제 저수준 메모리 배치뿐 아니라 중첩 리스트 접근과 인터프리터 연산 횟수 감소도 측정 결과에 영향을 줄 수 있음
* 현재 구현은 성능 비교를 위해 기존 2차원 데이터에서 별도의 1차원 리스트를 생성하므로 순간적으로는 두 표현을 함께 보유
* 따라서 현재 보너스 구현을 그대로 대규모 데이터의 “메모리 절약” 방법으로 해석하는 것은 적절하지 않음
* 실제 메모리 최적화를 목표로 한다면 처음부터 하나의 데이터 표현만 유지하는 설계가 필요

## 8. 패턴 자동 생성

* Cross와 X의 기하학적 규칙을 코드로 표현하여 임의 크기의 패턴 생성
* Cross

  * 중앙 행
  * 중앙 열
* X

  * 주대각선
  * 반대 대각선
* 사용자 입력 모드의 테스트 데이터와 성능 분석용 데이터를 동일한 생성 함수로 만들 수 있도록 구성
* 테스트용 행렬을 코드에 반복해서 작성하는 것을 줄이고 크기 변경에도 대응 가능

## 9. 현재 설계의 확장성

현재 프로그램은 두 개의 표준 라벨 `Cross`, `X`를 전제로 구성되어 있다.

새로운 형태가 추가된다면 다음 영역의 확장이 필요하다.

1. 새로운 외부 라벨을 내부 표준 라벨로 정규화
2. JSON에 새로운 필터 데이터 추가
3. 필터 로딩 시 허용하는 표준 라벨 확장
4. 현재 Cross/X 두 점수를 직접 비교하는 구조를 여러 필터의 점수를 순회하는 구조로 변경
5. 가장 높은 점수를 가진 라벨을 선택하되 epsilon 범위 내 공동 최대값에 대한 정책 정의
6. 새로운 라벨에 대한 테스트 데이터 추가

* 즉 현재 구조에서는 데이터 추가만으로 새로운 클래스가 자동 지원되지는 않음
* 클래스가 계속 증가할 가능성이 있다면 `label → filter` 딕셔너리를 순회하는 일반화된 판정 구조가 더 적합

## 10. 더 큰 입력에서 예상되는 문제

예를 들어 1000×1000 패턴의 경우:

* 필터 하나의 MAC에 1,000,000개 위치 접근 필요
* Cross/X 두 필터를 비교하면 최소 약 2,000,000번의 곱셈 및 누적 필요
* Python 반복문 자체의 인터프리터 오버헤드가 크게 누적
* Python의 2차원 리스트는 각 행과 각 숫자를 객체/참조 형태로 관리하므로 메모리 오버헤드도 큼
* 여러 필터를 동시에 사용하면 같은 입력을 반복해서 읽기 때문에 메모리 접근 비용도 증가

가능한 개선 방향:

* 데이터 구조 단순화
* 연속적인 메모리 접근
* 불필요한 데이터 복사 제거
* 여러 필터에 대한 반복 처리 일반화
* 병렬 처리
* 실제 수치 연산 환경에서는 벡터화 연산 및 전용 가속기 활용

## 11. CPU와 NPU 관점에서 본 MAC

* 현재 Python 구현은 MAC 과정을 학습하기 위해 연산을 순차적으로 수행
* 일반 CPU는 다양한 종류의 명령을 유연하게 처리하는 범용 프로세서
* Python 수준의 이중 반복문은 인터프리터 오버헤드까지 포함되므로 대규모 MAC 처리에는 특히 비효율적
* AI 연산은 같은 형태의 곱셈과 누적을 매우 많이 반복한다는 특징이 있음
* NPU는 여러 MAC 연산기를 병렬로 배치하여 다수의 곱셈·누적을 동시에 처리하도록 설계
* 데이터 이동을 줄이고 필요한 값을 재사용하는 구조도 대규모 행렬 연산 성능에 중요
* 따라서 문제 크기가 커질수록 단일 MAC 구현 방법보다 병렬성, 데이터 배치, 메모리 대역폭이 전체 성능에 큰 영향을 미침

## 12. 구현 과정에서 확인한 점

* MAC은 단순한 연산이지만 데이터 크기가 증가하면 반복 횟수가 빠르게 증가
* 부동소수점 값을 직접 동등 비교하는 방식은 판정 로직에서 위험할 수 있음
* 데이터의 의미와 표기 방법을 분리하면 외부 데이터 변경에 대응하기 쉬움
* 성능 측정에서는 무엇을 측정 구간에 포함하는지가 결과 해석에 중요
* 단순한 자료구조 변경도 반복 접근이 많은 코드에서는 유의미한 차이를 만들 수 있음
* 작은 테스트에서는 정상이어도 입력 크기와 클래스 수가 증가하면 현재 설계의 고정된 가정이 병목이나 확장 제약이 될 수 있음
